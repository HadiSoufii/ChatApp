# Nexa Chat – نسخه بازطراحی‌شده پروژه برنامه‌نویسی شبکه

این نسخه بر اساس سورس اولیه شما بازنویسی شده و برای **Windows Forms و .NET Framework 4.7.2** آماده شده است. رابط کاربری فارسی است و انتقال متن و نام کاربران با پروتکل JSON و پشتیبانی از Unicode انجام می‌شود؛ بنابراین پیام فارسی و ایموجی قابل انتقال است.

## اجرای پروژه

1. فایل `ChatApp.sln` را با Visual Studio در ویندوز باز کنید.
2. مطمئن شوید .NET Framework 4.7.2 Developer Pack روی سیستم نصب است.
3. از منوی **Build > Rebuild Solution** هر دو پروژه را Build کنید.
4. ابتدا پروژه `ChatpApp.Server` را اجرا کنید.
5. در پنل سرور پورت `5050` را نگه دارید و «شروع سرور» را بزنید. سرور روی تمام رابط‌های شبکه (IPv4) گوش می‌دهد.
6. پروژه `ChatpApp.Client` را یک یا چند بار اجرا کنید. در فرم ورود، نام، آدرس سرور، پورت و یکی از ۶ آواتار را انتخاب کنید.
7. برای آزمایش روی همان کامپیوتر از `127.0.0.1` استفاده کنید. برای کامپیوتر دیگر، IP محلی کامپیوتر سرور را وارد کنید و پورت TCP انتخاب‌شده را در Windows Firewall مجاز کنید.

## اصلاحات کامپایل در بسته اصلاح‌شده

برای رفع خطاهای کامپایل گزارش‌شده، این اصلاحات در سورس اعمال شده‌اند:

- ارجاع اسمبلی `System.Xml` به هر دو پروژه Server و Client اضافه شده است؛ این اسمبلی برای نوع‌های `XmlReader` و `XmlWriter` موردنیاز API سریال‌سازی JSON است.
- تمام سازنده‌های Thread با `new ThreadStart(...)` صریح شده‌اند تا بین overloadهای `ThreadStart` و `ParameterizedThreadStart` ابهامی باقی نماند.
- دستور `using System;` به `Program.cs` کلاینت اضافه شده تا ویژگی `STAThread` شناخته شود.

## امکانات پیاده‌سازی‌شده

- **چندکلاینتی:** هر اتصال توسط Thread مستقل مدیریت می‌شود و قطع یا دریافت پیام یک کلاینت، حلقه دریافت کلاینت‌های دیگر را متوقف نمی‌کند.
- **پروتکل ساختاریافته:** هر بسته یک نوع (`Type`) و داده‌های مشخص دارد. برای جلوگیری از ادغام یا تکه‌تکه‌شدن پیام‌های TCP، قبل از JSON طول بسته در قالب چهار بایت ارسال می‌شود.
- **فارسی و ایموجی:** پیام‌ها از طریق `DataContractJsonSerializer` و انتقال باینری شبکه ردوبدل می‌شوند؛ محدودیتی از جنس `ASCII` نسخه اولیه وجود ندارد.
- **رابط فارسی و راست‌چین:** فرم ورود، پنجره گفتگو و پنل مدیریت سرور دارای فایل‌های استاندارد `*.Designer.cs` و `*.resx` هستند؛ کنترل‌های اصلی در زمان طراحی ساخته می‌شوند و در Rider/Visual Studio قابل مشاهده و ویرایش‌اند. اندازه‌ی اولیه دو پنجره اصلی برای نمایشگرهای رایج لپ‌تاپ کوچک‌تر شده و دکمه‌های سربرگ و بخش‌های جدولی با تغییر اندازه فرم سازگارترند.
- **تم روشن و تاریک:** در پنل سرور، فرم ورود و پنجره گفتگو دکمه تغییر تم وجود دارد.
- **۶ آواتار:** سه آیکون با شخصیت زنانه و سه آیکون با شخصیت مردانه برای انتخاب کاربر.
- **نمایش پیام‌ها:** هر پیام نام/آواتار فرستنده، ساعت ارسال، رنگ مستقل برای پیام خودی/دیگران/سرور/سیستم و برچسب ویرایش دارد.
- **پیام خوش‌آمدگویی:** بعد از ورود، پیام خوش‌آمدگویی از سمت سرور به شکل کارت متفاوت نمایش داده می‌شود.
- **پاسخ، ویرایش و حذف:** پاسخ همراه نقل‌قول پیام اصلی است؛ کلیک روی نقل‌قول به پیام اصلی می‌رود. ویرایش و حذف فقط برای پیام‌های خود کاربر مجاز است و سرور مالکیت را بررسی می‌کند.
- **واکنش‌ها:** ❤️، 😂، 👍 و 🔥 زیر پیام قابل انتخاب هستند و شمارنده واکنش‌ها بین کاربران همگام می‌شود.
- **وضعیت پیام:** یک تیک = ارسال اولیه از کلاینت؛ دو تیک = تایید ثبت پیام توسط سرور؛ سه تیک = حداقل یک کاربر دیگر پیام را باز کرده و رسید خواندن ارسال کرده است.
- **سنجاق پیام:** مدیر سرور می‌تواند پیام موجود در فهرست پیام‌های پنل را انتخاب و در بالای گفتگوی همه کاربران سنجاق یا از سنجاق خارج کند.
- **وضعیت تایپ:** هنگام نوشتن، سایر کاربران نشانگر «در حال تایپ است…» را مشاهده می‌کنند.
- **پنل آنلاین سرور:** نام، آواتار، IP، ساعت اتصال و مدت آنلاین بودن هر کاربر نمایش داده می‌شود و مدیر می‌تواند کاربر انتخاب‌شده را قطع کند.
- **توقف سرور:** دکمه توقف، Listener و اتصال‌های شبکه را می‌بندد؛ پنجره مدیریت سرور باز می‌ماند و می‌توان سرور را دوباره شروع کرد.
- **فرم ورود:** پس از ورود موفق، فرم Login بسته و Dispose می‌شود و فقط فرم گفتگو باقی می‌ماند.
- **اعلان پیام:** هنگام دریافت پیام، صدای اعلان پخش می‌شود؛ اگر پنجره فعال نباشد، آیکون پنجره در Taskbar چشمک می‌زند و Balloon Tip نمایش داده می‌شود.
- **اتصال مجدد:** بعد از قطع اتصال، پنجره چت باز می‌ماند و کاربر می‌تواند بدون بازشدن دوباره فرم ورود، با همان نام و آواتار مجدداً متصل شود.

## ویرایش ظاهری فرم‌ها در Rider و Visual Studio

در نسخه‌های قبلی کنترل‌ها هنگام اجرای برنامه ساخته می‌شدند؛ به همین دلیل محیط طراحی فرم خالی دیده می‌شد. در این نسخه چیدمان اصلی هر سه فرم به فایل Designer منتقل شده است.

1. در پنجره Solution روی فایل `Login.cs`، `ChatGroup.cs` یا `ChatServer.cs` دوبار کلیک کنید. اگر فایل کد باز شد، از `Shift + F7` برای رفتن به Designer و از `F7` برای برگشت به کد استفاده کنید.
2. اگر پنجره Designer نمایش داده نشد، روی فایل فرم راست‌کلیک و گزینه **Open in Designer / View Designer** را انتخاب کنید.
3. کنترل‌های اصلی مثل پنل‌ها، دکمه‌ها، ورودی‌ها، جدول کاربران، سربرگ، نوار ارسال و ستون اعضا باید در صفحه طراحی دیده شوند.
4. فایل `*.Designer.cs` محل نگهداری چیدمان و ویژگی‌های ظاهری است و فایل اصلی `*.cs` رفتارها و ارتباط شبکه را نگه می‌دارد. برای تغییرات ظاهری از Designer استفاده کنید و منطق رویدادها را در فایل اصلی تغییر دهید.
5. بعد از تغییر فایل‌های پروژه، یک بار Solution را Reload و سپس `Rebuild Solution` کنید.

**نکته فرم گفتگو:** برای اینکه Rider بتواند فرم `ChatGroup` را بدون اتصال واقعی به سرور باز کند، یک سازنده عمومی بدون پارامتر اضافه شده است. این سازنده فقط کنترل‌ها و نمونه‌های نمایشی را می‌سازد و هیچ سوکتی باز نمی‌کند. برنامه هنگام اجرای عادی همچنان از سازنده‌ای استفاده می‌کند که اطلاعات کاربر و سوکت متصل را دریافت می‌کند. کارت پیام و کاربر نمونه در زمان اجرای واقعی حذف می‌شوند و داده‌های زنده جای آن‌ها را می‌گیرند؛ منطق ساخت حباب واقعی پیام در متد `BuildMessageCard` قرار دارد.

## فایل‌های مهم

| فایل | مسئولیت |
|---|---|
| `ChatpApp.Server/ChatServer.cs` | Listener، چندین نشست کلاینت، تاریخچه موقت، واکنش‌ها، رسید خواندن و مدیریت کاربران |
| `ChatpApp.Server/ChatServer.Designer.cs` | چیدمان قابل ویرایش پنل مدیریت سرور |
| `ChatpApp.Client/Login.cs` | رفتار فرم ورود، انتخاب آواتار و Handshake اولیه با سرور |
| `ChatpApp.Client/Login.Designer.cs` | چیدمان قابل ویرایش فرم ورود |
| `ChatpApp.Client/ChatGroup.cs` | رفتار گفتگو، ساخت حباب پیام‌ها، ویرایش/حذف/پاسخ، ایموجی، اعلان و اتصال مجدد |
| `ChatpApp.Client/ChatGroup.Designer.cs` | چیدمان قابل ویرایش پنجره گفتگو و نمونه نمایشی پیام/کاربر |
| `ChatpApp.Client/ChatProtocol.cs` | مدل بسته‌های شبکه و فریم‌بندی TCP در سمت کلاینت |
| `ChatpApp.Server/ChatProtocol.cs` | همان پروتکل مشترک در سمت سرور؛ باید با نسخه کلاینت هماهنگ بماند |
| `ChatpApp.Client/ThemeSettings.cs` | نگهداری انتخاب تم در سمت کلاینت |

## نکات فنی و محدودیت‌های فعلی

- تاریخچه پیام‌ها، سنجاق و واکنش‌ها در حافظه سرور نگهداری می‌شوند؛ با بسته‌شدن کامل برنامه سرور پاک می‌شوند. برای ماندگاری دائمی باید SQLite یا دیتابیس دیگری اضافه شود.
- رسید سه‌تیک زمانی ثبت می‌شود که حداقل یک کلاینت دیگر پیام را در پنجره فعال مشاهده کند؛ این پروژه وضعیت خواندن تک‌تک اعضای گروه را جداگانه گزارش نمی‌کند.
- سرور در این نسخه روی IPv4 و `IPAddress.Any` گوش می‌دهد. برای استفاده روی LAN، فایروال ویندوز باید پورت TCP انتخابی را مجاز کند.
- ارتباط فعلی TLS ندارد؛ این نسخه را فقط در شبکه مورد اعتماد و برای تمرین درسی اجرا کنید. برای استفاده واقعی باید `SslStream` و گواهی معتبر اضافه شود.
- پس از توقف سرور، پنجره کلاینت‌ها بسته نمی‌شود؛ وضعیت آفلاین و دکمه اتصال مجدد نمایش داده می‌شود.
- کدها در محیط فعلی قابل اجرای Windows Forms نبودند؛ در این محیط Build واقعی با Visual Studio/.NET Framework یا بازکردن Designer در Rider انجام نشده است. ساختار partial class، سازنده بدون پارامتر، ارجاعات `DependentUpon` و XML پروژه‌ها بررسی شده‌اند، اما **قبل از ارائه، هر فرم را در Rider باز کنید و Build Solution را روی ویندوز اجرا کنید**.

## سناریوی آزمایش پیشنهادی

1. سرور را روی پورت 5050 اجرا کنید.
2. سه کلاینت با نام‌های متفاوت وارد کنید.
3. از کلاینت اول یک پیام فارسی بفرستید و روی دو کلاینت دیگر نمایش نام، ساعت و آواتار را بررسی کنید.
4. از کلاینت دوم روی ❤️ کلیک کنید؛ شمارنده باید در همه کلاینت‌ها یکسان شود.
5. از کلاینت دوم به پیام اول پاسخ دهید، سپس پیام متعلق به کلاینت اول را ویرایش و حذف کنید.
6. در پنل سرور پیام را انتخاب و سنجاق کنید؛ بنر بالای چت‌ها باید به‌روزرسانی شود.
7. یکی از کلاینت‌ها را Minimize کنید و از کلاینت دیگر پیام بفرستید؛ اعلان صوتی/Taskbar را بررسی کنید.
8. سرور را Stop کنید؛ پنجره سرور باید باز بماند و کلاینت‌ها آفلاین شوند. سپس سرور را دوباره Start کرده و از کلاینت اتصال مجدد بزنید.


## رفع خطای SplitContainer در زمان شروع و محیط Designer

در فرم‌های `ChatServer` و `ChatGroup`، اندازه اولیه کنترل `_mainSplit` پیش از تعیین `Panel1MinSize` و `Panel2MinSize` مشخص شده است. این ترتیب ضروری است؛ چون هنگام `EndInit` ممکن است هنوز Layout والد اجرا نشده باشد و کنترل در اندازه پیش‌فرض ۱۵۰ پیکسلی باقی مانده باشد.

پس از نمایش فرم نیز متد `SetSafeSplitterDistance` فاصله جداکننده را با عرض واقعی کنترل محاسبه می‌کند. در نمایشگرهای کوچک‌تر، حداقل عرض پنل‌ها متناسب با فضای موجود کاهش می‌یابد تا مقدار نامعتبر به `SplitterDistance` اختصاص داده نشود.
